01

Understanding

先看理解：不是“编码后补文档”，而是研发治理闭环

文档既是云端确认并下发的研发约束，也是本地智能编码的伴生产物、云端人工审查的结构化载体，以及最终进入项目知识和正式基线的长期资产。

一句话理解
云端负责规划、治理、审查和沉淀，本地负责基于受控上下文执行研发；全过程产生的交互、代码、测试、文档和证据统一回流云端，形成与软件真实状态一致的工程文档。
云

云端治理 Agent

面向管理人员组织项目全局，负责需求、任务、规则、状态和人工决策。

  • 辅助需求分析和验收项确认
  • 任务拆分、依赖与人工卡点
  • 阶段预审、问题反馈和状态推进
端

本地研发 Agent 工作流

在真实代码、工具链和网络环境中完成研发，确保产出可运行、可验证。

  • 获取 Context Package
  • 多 Agent 编码、测试和审阅
  • 接收云端意见并整改复验
迹

Trace 与工程证据

Trace 还原过程，Evidence 证明结论，避免只相信 Agent 的“已完成”描述。

  • 交互、工具、文件和命令留痕
  • 提取工程事实并关联版本
  • 形成实现、验证和审批证据
知

文档与项目知识

将已确认的需求、设计、实现、测试和审查结论固化，并反哺后续 Agent。

  • 章节级增量生成与一致性校核
  • 软件与文档共同形成基线
  • 经验经审核后进入项目知识

“一致”不是文字相似，而是八个维度可相互验证

判断标准必须落到同一项目、任务、Harness Run 和软件版本上。

01

需求一致性

需求与验收项是否有真实实现和验证证据。

02

设计一致性

代码结构与关键机制是否符合已批准设计。

03

接口一致性

接口参数、返回、错误码与真实实现是否一致。

04

数据一致性

实体、表结构、约束和迁移脚本是否一致。

05

测试一致性

测试结论是否由真实执行结果和回归证据支撑。

06

状态一致性

“已完成、已通过”等状态是否经过门禁或人工确认。

07

过程一致性

是否使用正确上下文、工作流和强制人工卡点。

08

版本一致性

文档、代码、构建产物和审查结论是否绑定同一基线。

建设后的变化

  • 从“本地 Agent 自己做、云端只看结果”转为云端可治理、过程可下钻。
  • 从“用户重复解释项目”转为版本化项目上下文直接供给。
  • 从“Agent 说完成”转为 Trace、代码、测试和人工确认共同证明。
  • 从“项目结束补文档”转为文档随编码增量演化。

必须守住的边界

  • 云端 Agent 不能替代人工批准和风险接受。
  • Trace 不等于正式 Evidence，必须关联结论和版本。
  • 代码现状不能自动反向定义需求和设计。
  • 人工编写、已审核和已归档内容不得静默覆盖。
审

领导审阅时重点看什么

这个场景的价值不在“自动写了多少字”，而在是否形成云端可治理、本地可执行、过程可还原、结果可验证、问题可闭环、知识可复用的研发机制。

02

Process

再看流程：从云端需求规划到文档与知识沉淀

主流程不是单向“下发任务—返回结果”，而是通过人工卡点和结构化整改形成多轮闭环，直到软件、文档和证据共同满足阶段要求。

九步总体业务闭环

红色表示云端治理，蓝色表示本地执行，黄色表示审查决策，绿色表示资产固化。

01需求分析云端 Agent 辅助形成细化需求、验收项和待确认问题。
02任务规划拆分任务、依赖、工作流、产物要求和人工卡点。
03上下文下发形成版本化 Context Package，供本地用户和 Agent 使用。
04本地智能研发多 Agent 完成代码、测试、构建、文档候选和本地审阅。
05Trace 与产物回传上报交互、工具、文件变化、执行结果和 Artifact。
06云端预审提取事实和 Evidence，分析完成度、差异、风险和缺失。
07人工卡点管理人员决定通过、退回、补充、暂停或风险接受。
08整改与一致性校核问题返回本地复验，云端增量更新文档并双向校核。
09基线与知识软件、文档、证据共同固化，经验审核后反哺后续任务。

过程信息如何变成可用资产

这是避免“日志很多但无法审查、文档漂亮但没有依据”的关键转换链。

Trace记录发生了什么：消息、工具、命令、文件、测试和人工干预。
→
工程事实描述真实状态：修改范围、接口变化、测试执行和版本关系。
→
Evidence证明具体结论：需求已实现、验收已通过、风险已接受。
→
文档与知识固化已确认结论，并为后续任务和 Agent 提供长期上下文。

人工卡点不是最后审批，而是贯穿全过程

Agent 负责准备信息和建议，人负责确认业务边界、风险和正式结论。

卡点 01

需求与验收确认

目标、边界、验收方式是否准确。

卡点 02

任务与方案确认

拆分、依赖、技术方案和高风险变化是否合理。

卡点 03

本地执行确认

计划、范围外修改和高风险工具调用是否允许。

卡点 04

阶段成果审查

根据 Trace、产物和 Evidence 决定通过或退回。

卡点 05

基线与知识批准

正式文档、软件版本和项目知识是否可以发布。

03

Functions

最后看功能：八个模块支撑一条可治理研发闭环

功能不按“文档生成器”单点展开，而是覆盖云端规划、本地执行、过程证据、人工审查、文档基线和知识复用。

规划与供给层

把管理要求转化为本地可执行的任务、上下文和工作流。

2 个模块

执行与治理层

完成本地研发、全过程采集、云端预审和人工决策。

3 个模块

成果资产层

形成可信文档、共同基线和可持续复用的项目知识。

3 个模块

审

Review Focus

领导快速审查：重点判断六件事

以下问题能够帮助快速判断该场景是否真正形成产品闭环，而不是功能堆叠。

1. 云端是否真正能够治理本地 Agent？是否能下发任务、上下文、工作流和卡点，并获得真实执行过程，而不只是最终总结。
2. 本地是否真正基于项目权威上下文研发？每次 Run 是否明确使用哪个需求、设计、规则、知识和 Agent 版本。
3. Trace 是否能够转化为可信 Evidence？是否能证明需求实现、测试通过和风险接受，而不是简单保存大量日志。
4. 人工卡点是否有信息支撑并形成反馈闭环？管理人员是否能快速看到差异和风险，退回意见是否能被本地 Agent 继续执行。
5. 文档是否真正与智能编码双向一致？文档能否约束编码，代码变化能否定位并增量更新文档，错误代码是否会被直接包装成设计。
6. 项目经验是否经过确认后持续复用？知识是否有来源、范围、版本和人工审核，并实际进入后续 Context Package。

第一阶段建议

先用一个存量项目的一次中等复杂度需求变更，跑通“云端需求与任务—本地 Agent 研发—Trace 回传—云端预审—人工退回整改—文档增量更新—共同基线—知识候选”的完整闭环。
1 个项目1 类需求变更1 套本地工作流3 类文档1 条人工审查闭环

优先证明

  • 云端和本地上下文一致。
  • 关键过程可回放、结论有证据。
  • 人工问题可反馈本地整改。
  • 文档可按章节增量更新。
  • 软件和文档版本可绑定。

暂不追求

  • 复杂跨项目多 Agent 调度。
  • 全自动阶段批准。
  • 全量源码和对话集中存储。
  • 完整 GJB 文档包自动化。
  • 组织级知识图谱。
