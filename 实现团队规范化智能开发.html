01

Understanding

先看理解：规范化智能开发到底解决什么

它不是建设更强的代码生成工具，而是解决 AI 进入团队研发后，任务是否清晰、执行是否受控、结果是否可信、经验能否持续复用的问题。

一句话理解
个人智能编码解决“一个人如何更快完成局部开发”；团队规范化智能开发解决“一个团队如何在统一约束下，可靠地使用智能体完成软件研发”。

核心矛盾：局部速度提升，不等于团队效率提升

智能体显著提高产出速度，但如果任务、规范、边界和审查机制没有同步升级，团队协作成本可能不降反升。

AI 带来的局部加速

代码、文档、测试和方案能够在更短时间内形成。

  • 单个开发单元产出更快。
  • 方案探索和重复劳动减少。
  • 开发人员能够并行处理更多任务。
≠

团队面临的治理风险

变更数量增加后，隐性规范、重复建设和架构漂移更容易被放大。

  • 任务边界不清导致无效并行。
  • 局部正确但不符合项目工程语境。
  • 评审人员难以快速判断过程和结果是否可信。

通过四项机制实现规范化

规范化不是增加更多审批，而是把正确的约束放到正确的阶段。

规

规范可执行

将架构边界、代码约定、测试要求、安全规则和工作流形成版本化项目研发基线，由人和智能体共同使用。

控

任务可控制

由云端总控智能体辅助完成需求理解、任务拆分、依赖分析、风险分级和人工卡点设置。

证

过程可追溯

将交互、上下文、工具调用、代码变更、验证结果和人工决策组织为统一 Trace 证据链。

演

经验可演进

从 Trace 和评审结果提炼知识候选，经人工审核后反哺开发契约、任务模板和检查规则。

“规范化”覆盖研发全过程，而不只是代码格式

只有需求、任务、上下文、执行、产物、审查和知识同时被规范，团队智能研发才能形成稳定秩序。

需求规范化+ 任务规范化+ 上下文规范化+ 执行规范化+ 产物规范化+ 审查规范化+ 知识规范化= 团队规范化智能开发
01

需求

为什么做、范围是什么、达到什么结果。

02

任务

谁做什么、依赖什么、允许改什么、如何验收。

03

上下文

可以读取什么、必须参考什么、禁止访问什么。

04

执行

使用哪个智能体、工作流、工具、权限和验证步骤。

05

产物

形成哪些代码、测试、文档、报告和证据。

06

审查

哪个阶段由谁审查、依据什么、形成什么结论。

07

知识

哪些经验可沉淀、由谁批准、如何发布与回退。

云端与本地的职责边界

云端不直接替代本地研发，本地也不脱离团队治理独立运行；两者由 Trace 和任务执行包连接。

CLOUD CONTROL

云端：规划、约束、审查、沉淀

  • 维护项目研发基线与项目知识。
  • 辅助需求分析、任务拆分和风险分级。
  • 生成任务执行包并设置人工卡点。
  • 基于 Trace 和产物开展智能审查。
  • 形成整改意见和知识候选。
任务执行包↓版本化目标、边界、上下文、工作流与验证要求↑Trace 证据链
LOCAL RUNTIME

本地：理解、执行、验证、提交

  • 获取项目、需求、任务和研发基线。
  • 使用项目配置的 Agent、Skill 和工具。
  • 访问真实代码、依赖、构建与测试环境。
  • 完成分析、编码、测试、自审和修复。
  • 上报交互、变更、验证和产物信息。
云端负责“把研发组织正确”，本地负责“把任务执行正确”，Trace 负责“证明过程和结果确实正确”。
审

领导审阅时重点看什么

平台是否真正形成团队级研发秩序，而不是增加一个聊天入口；是否能将任务边界、人工责任和过程证据贯穿到每一次智能开发执行。

02

Process

再看流程：云端总控与本地研发如何形成闭环

总体流程以项目研发基线为起点，以任务执行包连接云端和本地，以 Trace 形成审查证据，以人工卡点控制关键决策，并将有效经验审核后反哺下一轮研发。

总体业务闭环

不是“需求直接交给 Agent 写代码”，而是先规划和约束，再执行和采证，最后审查、整改和沉淀。

STEP 01研发基线建立规范、架构、工作流、门禁和知识版本化
STEP 02需求理解与任务规划形成需求基线、任务图、风险和责任分工
STEP 03任务执行包下发明确目标、边界、上下文、工作流与验证要求
STEP 04本地受控智能研发开发人员控制 Agent 完成分析、编码、测试和自审
STEP 05Trace 与成果上报持续记录交互、变更、验证、产物和人工决策
STEP 06智能审查与人工卡点判断过程合规性、结果质量与阶段推进条件
STEP 07整改或阶段推进问题反馈本地修订，通过后进入合并或交付
STEP 08知识审核与反哺经验经人工审核后更新基线、模板和规则

流程围绕六类核心业务对象运行

每次研发都必须能够绑定明确版本和责任关系，避免聊天、代码、任务和审查记录彼此割裂。

OBJECT 01

项目研发基线

团队规范、架构边界、Agent、工作流、门禁和项目知识的统一版本。

OBJECT 02

需求基线

经确认的业务目标、范围、规则、验收标准和非本次范围内容。

OBJECT 03

任务执行包

下发本地的目标、边界、依赖、上下文、工作流和完成定义。

OBJECT 04

研发执行实例

某项任务在具体人员、环境、分支、Agent 和版本下的一次真实运行。

OBJECT 05

Trace 证据包

经过组织和筛选、可供过程与成果审查使用的任务级证据集合。

OBJECT 06

审查单与知识候选

记录审查依据、问题、结论、整改要求及待审核的经验沉淀。

按阶段快速审阅流程输入、处理与输出

选择阶段查看其核心动作、控制要求和可验收成果。

阶段目标
让规范成为可执行基线

参与角色

  • 管理人员与技术负责人确认规则。
  • 云端总控智能体辅助识别显性规范和历史实践。
  • 平台管理员配置 Agent、工具、权限与集成。
输出：版本化项目研发基线、工作流、门禁、Owner 和发布记录。

主流程

  1. 导入项目说明、架构文档、代码仓库和团队规范。
  2. 识别项目级、模块级、文件级和任务级约束。
  3. 配置不同风险任务的 Agent 工作流、门禁和人工卡点。
  4. 经责任人确认后发布基线版本。
  5. 已启动任务继续绑定原版本，避免规则变化污染历史执行。
阶段目标
把原始诉求变成可执行任务图

关键控制

  • 缺少目标、范围和验收标准不得直接编码。
  • 公共契约、数据、安全和架构变更必须先确认方案。
  • 并行与互斥关系必须显式说明。
输出：需求基线、任务清单、依赖图、风险等级、责任人与人工卡点。

主流程

  1. 提炼业务目标、使用对象、核心流程和业务规则。
  2. 识别信息缺失、冲突和待确认事项。
  3. 形成可核对的验收标准。
  4. 识别影响模块、公共契约、数据、安全和集成风险。
  5. 拆分契约任务、独立实现任务、共享资产任务和集成验证任务。
  6. 人工调整并确认需求与任务规划。
阶段目标
把计划转成可直接执行的任务包

关键控制

  • 任务包绑定需求、研发基线和上下文版本。
  • 明确允许修改和禁止修改范围。
  • 重大范围或契约变化后必须重新生成。
输出：任务执行包、上下文包、工作流、权限和验证清单。

主流程

  1. 根据任务类型和风险选择适用工作流。
  2. 装配相关需求、代码、接口、数据模型和历史案例。
  3. 注入必须复用能力、禁止事项和质量要求。
  4. 绑定 Agent、Skill、工具权限和验证命令。
  5. 下发本地，由开发人员确认环境和可执行性。
阶段目标
在真实工程环境中受控研发

关键控制

  • 智能体只能在批准范围和权限内操作。
  • 高风险事项必须暂停并请求人工确认。
  • 不允许静默重试掩盖失败原因。
输出：代码、测试、文档、验证结果、风险说明和待审查成果。

主流程

  1. 创建任务分支、工作区或隔离会话。
  2. Agent 读取任务包并形成实现计划。
  3. 开发人员控制其完成分析、编码、测试、自审和修复。
  4. 执行构建、测试、扫描和越界检查。
  5. 形成变更说明、验证证据和未解决问题。
  6. 全过程持续采集并关联 Trace。
阶段目标
用证据判断过程和结果是否可信

双重审查

  • 过程规范性：是否按批准的任务包和工作流执行。
  • 结果质量：是否满足需求、架构、测试与交付要求。
  • 关键结论由责任人作出，不由 Agent 代替。
输出：审查单、风险问题、整改任务、通过/驳回/有条件通过结论。

主流程

  1. 云端汇总需求、任务、基线、Trace 和成果物。
  2. 总控智能体生成审查摘要、问题清单和待人工确认项。
  3. 责任人完成需求、方案、阶段成果或合并交付卡点。
  4. 问题关联到任务、文件、Diff 或验证项。
  5. 本地修订后重新形成 Trace 并复核。
  6. 通过后进入合并、交付或下一阶段。
阶段目标
把一次经验变成后续可复用约束

关键控制

  • 原始 Trace 不等于正式知识。
  • 单次评审意见不自动升级为团队规范。
  • 知识必须标明来源、适用范围和版本。
输出：知识候选、审核记录、正式知识、基线更新与效果数据。

主流程

  1. 从评审意见、门禁失败、越界修改和优秀实践中识别经验。
  2. 生成知识候选并说明来源、适用范围和预期作用。
  3. 责任人判断其正确性和通用性。
  4. 审核通过后发布为开发契约、任务模板、上下文或检查规则。
  5. 跟踪使用效果，对无效知识修订、停用或回退。

流程中的六类人工卡点

Agent 可以辅助分析和给出建议，但重大需求、架构、阶段推进和知识发布必须保留清晰的人类责任。

GATE 01

需求确认

确认需求理解、范围和验收标准。

GATE 02

任务规划确认

确认拆分、依赖、并行边界和责任分工。

GATE 03

高风险方案确认

确认架构、数据、安全和公共契约变更。

GATE 04

阶段成果审查

判断过程合规和成果进入下一阶段条件。

GATE 05

合并或交付批准

决定是否允许进入主干、制品或交付环节。

GATE 06

知识发布确认

确认经验是否可复用及其正确适用范围。

03

Functions

最后看功能：六个核心模块支撑完整研发闭环

功能不按传统菜单堆叠，而是围绕“建立基线、规划任务、下发上下文、本地执行、云端审查、知识演进”组织，并明确每个模块可核对的产出和验收价值。

云端治理能力

负责项目研发基线、需求任务规划、审查决策和知识发布。

规划与决策

本地研发能力

负责真实工程环境中的 Agent 工作流、编码测试和过程采集。

执行与验证

云地协同能力

通过任务执行包、Trace、整改反馈和工程系统集成连接两端。

贯穿全流程
01

项目研发基线与智能体能力管理

把团队规范、工程事实和 Agent 能力形成可版本化、可发布的统一研发基线。

›

职责：作为团队智能研发的基础配置中心，承接项目目标、架构边界、研发规范和智能体能力，形成所有任务共同遵循的执行依据。

  • 维护项目目标、技术栈、模块职责和依赖边界。
  • 管理编码、测试、安全、分支和提交规范。
  • 配置 Agent、Skill、模型、工具、MCP 和研发工作流。
  • 配置质量门禁、人工卡点、代码 Owner 和评审路由。
  • 支持基线审批、发布、版本管理和回退。

验收重点

  • 每次执行绑定唯一研发基线版本。
  • 历史版本不可被覆盖，可查询发布和审批记录。
  • 规则、工作流和 Agent 能力具有明确适用范围。
  • 基线变化不自动污染已启动任务。
02

需求理解与任务规划

把原始需求转化为可确认、可拆分、可执行和可验收的需求基线与任务图。

›

职责：作为研发任务进入平台的总控入口，承接原始需求和项目研发基线，完成需求结构化、风险识别、任务拆分和责任分配。

  • 提取业务目标、范围、规则和验收标准。
  • 识别缺失信息、冲突和待确认事项。
  • 分析影响模块、公共契约、数据、安全与集成风险。
  • 生成任务依赖图、并行建议和互斥修改范围。
  • 推荐风险等级、责任人、Owner、评审人和人工卡点。

验收重点

  • 任务包含目标、边界、验收和验证方式。
  • 高风险任务能够识别并强制进入方案确认。
  • 任务拆分、依赖和并行关系可人工调整。
  • 需求和任务规划具有版本及确认记录。
03

任务上下文装配与本地下发

把云端规划转化为本地人员和 Agent 可以直接执行的受控任务包。

›

职责：作为云端规划与本地执行之间的衔接能力，承接已确认任务，生成目标、边界、上下文、工作流和验证要求完整的任务执行包。

  • 检索相关代码、接口、文档、数据模型和历史案例。
  • 推荐必须复用的组件和公共能力。
  • 配置允许修改、禁止修改和敏感访问范围。
  • 绑定研发基线、上下文、Agent 工作流和验证命令版本。
  • 支持任务包生成、审批、同步、更新和失效控制。

验收重点

  • 任务包可追溯到需求、任务和研发基线。
  • 本地能够明确知道“做什么、怎么做、不能做什么”。
  • 重大范围或契约变化后旧任务包自动失效。
  • 上下文来源、版本和适用范围可核对。
04

本地智能研发执行与过程采集

在真实工程环境中完成分析、编码、测试、自审和修复，并形成全过程 Trace。

›

职责：作为真实研发环境中的执行载体，承接任务执行包，由开发人员控制本地 Agent 工作流完成研发，并采集关键交互、操作和成果。

  • 同步项目和任务，创建分支、工作区或隔离环境。
  • 启动 Agent 工作流并执行计划、编码、测试和修复。
  • 控制高风险操作暂停、人工确认和权限边界。
  • 采集交互、工具调用、命令、文件变更和验证结果。
  • 支持断网缓存、失败补传、敏感信息过滤和脱敏。

验收重点

  • Agent 不得越出批准的工作区和操作权限。
  • 每次执行绑定人员、环境、分支、任务和版本。
  • 关键文件 Diff、命令结果和人工操作可完整回溯。
  • 失败、暂停、取消和人工接管状态清晰。
05

智能审查、人工卡点与阶段推进

基于需求、基线、Trace 和成果判断过程是否合规、结果是否满足要求。

›

职责：作为研发过程和成果的质量控制中心，汇总任务证据，开展过程规范性与结果质量双重审查，生成整改意见并控制阶段推进。

  • 检查任务包、工作流、上下文和人工卡点执行情况。
  • 分析需求、代码、测试、文档和变更说明的一致性。
  • 识别越界修改、公共契约、共享资产和架构边界风险。
  • 生成智能审查摘要、风险清单和待人工确认项。
  • 支持通过、驳回、有条件通过、整改复核和阶段流转。

验收重点

  • 审查结论具有依据、责任人、时间和版本。
  • 过程合规与结果质量能够分别给出结论。
  • 问题可关联到任务、文件、Diff 或验证项。
  • 未满足关键卡点或证据要求时不得误推进。
06

Trace 治理与项目知识演进

把过程证据、审查意见和任务结果转化为可信、可审核、可复用的项目资产。

›

职责：作为团队研发经验沉淀和持续优化中心，承接全过程 Trace 与审查结果，形成任务时间线、证据包、知识候选和研发基线更新。

  • 关联项目、需求、任务、执行实例、产物和审查记录。
  • 形成任务时间线、关键决策和阶段证据包。
  • 归类评审意见、失败原因、越界行为和优秀实践。
  • 生成知识候选并分析来源、适用范围和影响。
  • 支持人工审核、发布、版本、回退和效果评估。

验收重点

  • 能够回答“谁基于什么，通过什么过程，产生了什么结果”。
  • 原始 Trace、经验候选和正式知识分层管理。
  • 未经审核的经验不得自动成为正式规范。
  • 知识发布后能够追踪使用和问题改善效果。

Roadmap & Acceptance

建设重点：先验证一条真实任务的完整闭环

第一阶段不追求复杂多 Agent 编排和全面工程集成，先证明平台能够围绕一个真实研发任务完成云端规划、本地执行、过程上报、云端审查和整改通过。

第一阶段核心验收问题

能否围绕一个真实研发任务，稳定完成“云端需求与任务规划 → 任务执行包下发 → 本地 Agent 受控执行 → Trace 上报 → 云端审查 → 整改闭环 → 阶段通过”。
项目研发基线任务执行包本地 Agent 工作流基础 Trace人工卡点整改反馈

第一阶段优先纳入

  • 项目研发基线和版本绑定。
  • 云端需求理解、任务规划和人工确认。
  • 任务执行包生成与本地同步。
  • 本地 Agent 工作流启动与基础执行控制。
  • 交互、文件变更、测试结果和产物 Trace。
  • 云端审查摘要、整改反馈和阶段流转。

第一阶段暂不追求

  • 复杂全自动多 Agent 协商。
  • 自动合并和自动生产发布。
  • 覆盖全部技术栈和工程系统。
  • 一次性沉淀完整隐性规范。
  • 未经人工审核的知识自动发布。
  • 把所有原始日志都作为审查证据。

分阶段形成能力

先形成最小闭环，再强化工程质量，最终形成知识驱动的持续演进。

PHASE 01

形成最小闭环

证明云端规划、本地执行、过程上报、审查整改能够贯通。

  • 项目研发基线。
  • 需求与任务规划。
  • 任务执行包。
  • 本地工作流与基础 Trace。
  • 审查卡点和阶段流转。
PHASE 02

强化工程质量控制

接入现有工程系统，增强范围、质量和集成风险判断。

  • Git、PR/MR 和 CI 集成。
  • 越界修改与共享资产冲突检测。
  • 需求到代码、测试和文档映射。
  • 分级门禁和证据包优化。
PHASE 03

形成知识驱动演进

让规范、任务模板和 Agent 工作流根据真实研发结果持续改善。

  • 经验与知识候选提炼。
  • 知识审核、版本发布和回退。
  • 同类问题复发分析。
  • Agent 与工作流效果评测。
  • 组织级知识复用。

建议重点度量

评价团队开发是否更稳定、更高效，而不是统计 Agent 生成了多少代码。
