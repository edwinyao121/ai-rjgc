INTELLIGENT SOFTWARE FACTORY · 2-WAY CHOICE

智能软件工厂两种实现方案

二选一，只比一件事：编码、AI 生成、自动化测试，主要在服务端跑，还是在客户端跑。 工厂要的是门禁、证据与基线——不是必然等于 WebIDE。

对等计分 场景化选型 去掉未证实断言 与云端治理 + 本地执行一致
默认推荐
选方案2：服务端管控，客户端执行

用服务端把工厂「管严」，用客户端把工程「做真」。仅在不能装客户端、必须纯浏览器闭环等硬约束下，改选方案1。

共同前提（不算差异点）

  • 企业级 Git 等源码库是协作与归档主通道，不假设「代码只在个人硬盘」。
  • 「是否算完成」由平台门禁与证据裁定，不单靠口头或本地自测绿。
  • AI 可优先用中心推理 / 模型 API；仅在自建端侧或平台 GPU 时才把高端显卡成本算进去。

1实现合理性 · 落地是否顺畅 互有胜负 ▼

方案1

优点
  • 执行环境易统一，减少换机结果漂移（需接近目标运行时）
  • 模型与 Agent 策略易统一
  • 留痕路径短，门禁与执行同机闭环顺
缺点
  • 隔离与多租户边界建设重
  • 集中执行放大故障与安全半径
  • 断网/平台故障易全面停工
  • 统一环境 ≠ 质量不可作假，可信靠门禁设计

方案2

优点
  • 执行面薄、见效快，不必先建完整 WebIDE 沙箱
  • 调试压力在开发机；可用中心 API，不必全员 GPU 农场
  • 弱网可本地降级编辑，恢复后补传
  • 贴合政企内网真实工具链
缺点
  • 环境一致性要靠镜像/标准机设计
  • 门禁与 Evidence 必须产品化，否则名存实亡
  • 客户端分发与强制升级是长期功课
  • 离线/死机下的状态同步复杂
2设计合理性 · 架构是否科学 更偏方案2 ▼

方案1

优点
  • 流水线形态直观，管理认知成本低
  • 访问控制集中，便于审计（≠ 源码带不走）
  • 能力一次上线、全员可得
缺点
  • 任务 / 算力 / WebIDE / 测试易深度耦合
  • 平台故障 = 全员无法编码
  • 把 IDE 焊进工厂本体，抬高不必要复杂度

方案2

优点
  • 控制面与执行面分离，职责清晰
  • 平台短时故障时仍可能本地改代码
  • 更易与 Git / CI / 制品库共存
缺点
  • 管控做薄会退化成工具集
  • 工作区 / Trace / 门禁同步是设计难点
  • 大文件回传有独立工程量
3使用模式 · 日常是否舒服 更偏方案2 ▼

方案1

优点
  • 理想情况下浏览器零安装，利于试用与借调
  • 环境与算力对个人透明
  • 在线只读共享方便
缺点
  • 网速与大仓库敏感，体验常弱于本地
  • 与资深研发本地 IDE 习惯冲突
  • 断网即停写；GUI / 外设调试吃力

方案2

优点
  • 贴合既有 IDE 习惯，接受度通常更高
  • 本地性能与离线编辑友好
  • 内网现场工具链友好（本机仍 ≠ 生产）
缺点
  • 首次配置与管理员权限是落地坎
  • 换机成本高，需标准镜像或远程开发机
  • 必须强制中央库与评审，否则协作失败
4技术合理性 · 路线是否靠谱 互有胜负 ▼

方案1

优点
  • 策略与模型生效路径短，利于评测
  • 受控环境便于标准回归（≠ 生产等价）
  • WebIDE 组件成熟；Agent 多租户集成面仍新
缺点
  • 集中算力与隔离投入高
  • 多租户调度、密钥与代码隔离难
  • 在线工作区存储膨胀；部分工具链别扭

方案2

优点
  • 平台硬件剖面更低；模型可与 WebIDE 解耦
  • 执行保真度潜力高
  • 治理 / VCS / CI / 客户端可分期演进
缺点
  • 多 OS 适配与最低版本门禁必做
  • 日志与失败样本必须回传
  • 端侧 Agent 安全半径在终端，需约束审计
  • 强依赖本地大模型时更新慢；走中心 API 则大幅缓解
5部署模式 · 落地与运维 更偏方案2 ▼

方案1

优点
  • 公有云 / 私有化整包均可，统一入口清晰
  • 服务端集中升级
  • 集团组织、权限、审计集中
缺点
  • 私有化资本开支与 SRE 门槛高
  • 气隙机房离线供应链重
  • 随人数扩容的是整平台，成本陡

方案2

优点
  • 服务端部署相对轻
  • 契合「中心服务器 + 终端执行」网络布局
  • 人数增长时平台弹性压力较小
缺点
  • 终端运维与版本治理压力大
  • 无管理员权限时必须域推送 / 静默部署
  • 必须拒绝过旧客户端过门禁

一般情形下谁更有利

关注点 更有利 一句话原因
首期上线速度 方案2 少建 WebIDE / 全量在线沙箱
编码体验与工具链保真 方案2 本地 IDE + 真实环境
零安装 / 快速借调试用 方案1 浏览器进入
环境与策略「默认就统一」 方案1 方案2 靠镜像与强制更新补
平台故障时能否继续改代码 方案2 工厂流程仍可能停，编辑器不必一起死
集中审计入口与管理叙事 方案1 方案2 同等审计靠回传与门禁设计
私有化 TCO（默认中心推理/API） 方案2 往往更优 方案1 易低估隔离与会话；方案2 易低估终端治理
与现有 Git / CI 共存 方案2 更不易做成「替代一切的巨石」

选型结论（二选一）

默认方案2 · 硬约束下改选方案1

默认：选方案2

  1. 工厂核心是过程、证据与基线，不是 WebIDE；权威在服务端，干活在客户端。
  2. 体验与内网工具链决定采用率；方案1 失败模式是「平台很重、一线不用」。
  3. TCO 更可控：模型走中心推理/API 时，钱应花在门禁、证据、策略与客户端治理，而不是过早建全员在线编码集群。
  4. 方案1 的统一环境、集中采集等优势，可用标准开发镜像 + 强制回传 + 中心策略在方案2 中逼近。

一句话：用服务端把工厂「管严」，用客户端把工程「做真」。

何时改选方案1

下列条件同时或强势成立时：

  • 终端禁止安装客户端，只允许浏览器
  • 必须以统一在线工作区为唯一交付界面
  • 能持续投入多租户隔离、高可用与集中执行
  • 工具链可被 Web/远程完整覆盖，无强本机外设依赖

方案2 落地五条底线

守不住就不是工厂，只是个人工具合集

1

完成/合入以平台门禁 + Evidence 为准，本地绿不能替代

2

Agent 规则、模型路由、最低客户端版本由服务端强制

3

Trace、测试报告、关键制品必须回传，支持抽检复盘

4

源码协作以中央库为准，禁止只在个人电脑流传

5

终端权限与 Agent 能力有安全边界，禁止全开放 shell
