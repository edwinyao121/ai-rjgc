智能化软件
功能测试与修复

不是让 AI 多生成一些用例、把失败测试改绿，而是建立从功能正确性依据、多方式测试、失败归因到受控修复与影响回归的可信闭环。

01

Understanding

先看理解：智能化的核心不是“自动”，而是“可信判断与闭环”

普通自动化测试解决已知脚本如何重复执行；智能化功能测试与修复进一步解决应该测什么、怎样组合测试、失败属于谁、是否允许修复、修复后如何证明没有引入新问题。

一句话理解
以需求、验收标准和业务规则定义“什么是正确”，由 Agent 结合代码变更和历史缺陷动态设计测试，依据真实执行证据完成失败归因，在授权边界内修复并通过影响回归证明问题真正闭环。
RESULT 01

测得准

测试目标有依据，测试场景覆盖业务行为，断言不是模型猜测，环境和数据基线可复现。

RESULT 02

定位准

综合断言、日志、请求响应、环境、数据、契约和代码差异，区分需求、测试、环境与代码问题。

RESULT 03

修得对

先归因再修复，限制修改范围，禁止删除测试和降低断言，研发人员确认工程方案。

RESULT 04

证得清

测试、归因、补丁、回归和人工意见都绑定需求、代码版本、环境和 Trace，结论可复核。

智能化体现在哪里

不是用一个大模型替代所有测试工具，而是让 Agent 在正确依据、真实工具和人工责任之间完成智能连接。

1

理解测试目标

从需求、验收项和业务规则中提取角色、前置条件、操作、结果和异常分支。

2

动态设计测试

结合代码 diff、调用关系和历史缺陷，选择本次真正需要执行的场景和回归集。

3

选择执行方式

根据测试对象调用接口、UI、端到端、状态、权限或人工辅助测试工具，而非固定一种方式。

4

融合多源证据

把断言结果、日志、截图、请求响应、数据库状态和环境信息形成统一证据链。

5

辅助归因修复

先识别需求、用例、数据、环境、契约或代码问题，再生成候选方案和最小补丁。

6

选择影响回归

根据修改影响动态验证相关接口、页面、权限、状态流转和历史缺陷，避免只重跑原用例。

审

领导审阅时重点看什么

系统是否能说明“依据什么认为功能正确、为什么选择这些测试、失败为什么归到这个原因、修复为什么不会破坏其他功能”，而不只是展示生成了多少用例和执行了多少次测试。

02

Accuracy

测试准确性：用五道保障建立可置信结论

测试准确性不是模型“判断得像不像”，而是由正确性事实源、场景覆盖、断言可信、环境可复现和多证据一致共同保证。

正确性基线×场景覆盖×断言可信×环境可复现×证据一致＝可置信测试结论

正确性事实源

先确定“什么叫通过”，再生成测试。

  • 需求与验收标准
  • 业务规则与状态机
  • 接口契约与页面行为
  • 历史缺陷与交付约束

场景覆盖推导

从业务行为而非代码外形推导覆盖。

  • 正常与异常路径
  • 角色与权限路径
  • 状态流转与反向操作
  • 边界、历史与变更影响路径

断言来源可信

每条预期结果都要知道来源。

  • 关联验收项或规则
  • 区分正式事实与 Agent 推断
  • 不确定断言必须人工确认
  • 禁止为通过而降低断言

环境与数据基线

避免把环境和数据问题误判为功能缺陷。

  • 绑定代码、配置和依赖版本
  • 测试前健康检查
  • 前置数据状态校验
  • 支持复现和重跑

多证据交叉验证

不依赖单一截图或单一断言。

  • 页面行为与接口响应
  • 日志与错误堆栈
  • 数据库或状态变化
  • 工具执行与环境信息

准确性贯穿五个控制点

不是测试执行完成后才检查准确性，而是在测试前、测试中、失败后、修复后和放行前逐层控制。

测试前：可测试性检查

验收标准缺失、冲突或只能依赖推断时，不直接生成正式通过结论。

设计时：覆盖与断言审查

关键验收项必须有用例，关键用例必须有明确断言来源。

执行时：环境与证据校验

先证明执行环境可用，再采集足够证据判断行为是否符合预期。

失败后：归因可信度

低可信归因不得自动修改代码，应补充证据或由研发人员确认。

修复后：双重回归

既验证原问题消失，也验证相关业务行为没有被新的修改破坏。

可信结论必须具备

  • 关联需求、规则或历史缺陷。
  • 绑定代码和环境基线。
  • 保留真实执行结果和证据。
  • 说明已覆盖范围和未覆盖风险。

不能作为通过依据

  • Agent 自述“测试已通过”。
  • 只有脚本退出码，没有业务断言。
  • 只验证单一快乐路径。
  • 通过删除测试或降低断言获得绿色结果。
03

Methods & Modes

测试方式与测试模式：不是固定脚本，而是按任务动态组合

智能化功能测试应同时由需求、代码变更和历史风险驱动，并根据测试对象组合接口、页面、端到端、权限、状态和人工探索等方式。

需求驱动验证验收标准、业务流程和异常规则
＋
变更驱动根据 diff、调用关系和依赖选择增量回归
＋
历史驱动复用历史缺陷、高风险路径和团队规则

七类主要测试方式

不同方式验证不同层面的业务事实，系统应按任务组合，而不是把功能测试等同于 UI 自动化。

业务黑盒

需求验收测试

从需求、用户故事和验收标准验证功能是否符合业务预期。

  • 适合新功能验收
  • 输出需求覆盖矩阵
  • 关键结果由业务规则断言
接口层

接口与契约测试

验证输入输出、状态码、错误码、字段约束和服务间兼容性。

  • 定位快、执行稳定
  • 适合前后端及服务协同
  • 支持契约差异分析
用户视角

页面与端到端测试

验证真实用户操作、页面反馈和跨模块业务流程。

  • 覆盖按钮、表单、路由和提示
  • 采集截图或视频证据
  • 适合核心业务链路
业务规则

权限与状态流转测试

验证不同角色能否操作以及业务状态能否按规则转换。

  • 正向、拒绝和反向操作
  • 越权和不可达状态检查
  • 适合审批、流程和核心业务
输入空间

边界与数据校验测试

验证空值、格式、范围、组合条件和数据关联约束。

  • Agent 可辅助生成高价值数据
  • 前置条件需真实校验
  • 避免只做随机数据轰炸
变更视角

影响范围回归测试

根据代码、接口、数据模型、路由和状态机影响动态选择回归集。

  • 避免固定全量或只重跑失败用例
  • 解释为什么选择这些回归
  • 显式展示未覆盖风险
历史视角

历史缺陷回归测试

将已发生问题转化为长期回归资产，防止相同缺陷再次出现。

  • 关联原缺陷和修复版本
  • 进入高风险路径库
  • 可反哺后续 Agent 测试设计
人机协同

探索式与人工辅助测试

对规则不完整、交互体验和复杂组合场景，由 Agent 提示路径并辅助人员执行。

  • 不强行自动化所有场景
  • 记录人工步骤与证据
  • 适合低确定性和体验类问题

测试模式：同时考虑任务触发与人机控制强度

“测试模式”不应只有一种自动化级别，应根据任务类型和风险选择。

按任务触发划分

决定本次测试从哪里开始、重点验证什么。

新功能验收模式以需求和验收标准为主，覆盖核心流程、异常、权限和状态。需求驱动
代码变更增量模式以 diff 和依赖关系为主，动态生成受影响测试与回归范围。变更驱动
缺陷复现修复模式先稳定复现和保留失败证据，再归因、修复和双重回归。问题驱动
版本发布验收模式汇总必测项、关键回归、剩余风险和版本证据，支撑放行审查。发布驱动

按人机控制划分

决定 Agent 可以自动执行到什么程度。

人工辅助模式Agent 生成场景、步骤和分析建议，研发人员确认并主导执行。低确定性 / 新领域
受控自动模式在预先确认的标准和授权范围内，Agent 自动执行测试和低风险修复。边界清晰 / 可回归
严格审查模式高风险功能由人员确认测试计划、技术归因、补丁和放行，Agent 只辅助。权限 / 核心流程 / 跨系统
选择因素 01

正确性是否明确

验收标准越不明确，越需要人工辅助和需求澄清。

选择因素 02

修改影响是否可控

影响范围越大、跨系统越多，审查和回归强度越高。

选择因素 03

测试资产是否成熟

稳定用例、数据和环境越充分，越适合受控自动执行。

选择因素 04

风险是否可逆

涉及权限、状态机、数据口径和历史数据时采用严格审查。

04

Process

总体流程：从正确性基线到测试、归因、修复和回归

流程主线围绕功能正确性推进；责任边界用于控制何时本地闭环、何时升级管理侧，而不是替代测试业务主线。

智能化测试修复闭环

先明确正确，再选择方式；先归因，再修复；修复后既验证原问题，也验证影响范围。

STEP 01任务与变更输入需求、验收项、缺陷、代码版本和重点风险
STEP 02正确性基线整理业务规则、契约、页面行为和历史缺陷
STEP 03选择测试模式新功能、增量、缺陷或发布；人工辅助或受控自动
STEP 04设计测试策略组合测试方式、场景、用例、数据和断言
STEP 05环境与数据准备绑定代码环境基线，执行健康和前置条件检查
STEP 06真实测试执行调用现有工具并采集日志、截图、响应和状态变化
STEP 07失败归因区分需求、用例、数据、环境、契约和代码问题
STEP 08受控修复研发人员确认方案，Agent 在授权范围内生成或应用补丁
STEP 09双重回归原问题验证＋影响范围回归＋新增失败识别
STEP 10审查与沉淀云端汇总证据，人员放行，经验形成知识候选

四类典型流程

不同任务共享总体闭环，但测试起点、重点和结束条件不同。

模式目标
证明新功能符合业务预期

测试重点

  • 需求和验收项覆盖。
  • 核心路径、异常、权限与状态。
  • 未明确规则进入澄清。

主流程

  1. 提取角色、前置条件、操作和预期结果。
  2. 形成需求覆盖矩阵和场景集合。
  3. 组合接口、UI、状态和数据测试。
  4. 研发人员确认关键断言。
  5. 执行、归因、修复和回归。
  6. 形成验收证据和未覆盖风险。
模式目标
用最小测试集覆盖真实变更风险

测试重点

  • 代码 diff 与依赖关系。
  • 相关接口、页面、数据和状态。
  • 历史缺陷和公共组件影响。

主流程

  1. 绑定修改前后代码基线。
  2. 分析改动文件、调用关系和契约变化。
  3. 映射受影响需求与测试资产。
  4. 形成增量测试集和必要冒烟集。
  5. 执行测试并根据新证据扩大或收缩范围。
  6. 输出回归选择理由和未覆盖风险。
模式目标
以可复现证据证明问题真正修复

测试重点

  • 修复前必须稳定复现。
  • 归因先于修改代码。
  • 原问题与相邻功能双重回归。

主流程

  1. 整理现象、步骤、数据、环境和期望结果。
  2. 复现并保存失败证据。
  3. 区分用例、数据、环境、契约或代码根因。
  4. 生成最小修复方案并由研发人员确认。
  5. 执行原问题验证。
  6. 根据修改影响执行相关回归。
模式目标
证明版本达到可放行状态

测试重点

  • 必测验收项和核心业务路径。
  • 变更影响、历史缺陷和关键冒烟。
  • 剩余风险、豁免和证据完整性。

主流程

  1. 锁定代码、环境和制品版本。
  2. 汇总本版本需求、变更和缺陷。
  3. 形成发布级测试策略和必测集。
  4. 执行并汇总所有阻塞项。
  5. 云端 Agent 形成审查摘要和风险清单。
  6. 管理人员决定放行、退回或豁免。
05

Attribution & Repair

失败归因与受控修复：避免“为让测试变绿而改错对象”

一次测试失败并不等于代码缺陷。系统必须先判断失败来源，再决定修改需求、测试、数据、环境、契约还是代码。

需求与验收问题规则缺失、冲突或业务预期无法确定，升级管理侧确认。
测试用例与断言问题步骤、前置条件或预期结果错误，由研发/测试人员修正。
测试数据问题状态、权限或关联关系不满足条件，重建或校验数据。
环境与依赖问题服务、配置、网络或依赖不可用，先恢复环境再重试。
契约与代码缺陷接口或业务实现不符合已确认规则，进入受控修复。

三种修复执行级别

不是所有缺陷都自动修改；自动化程度由正确性确定度、修改风险和回归能力共同决定。

建议级

只分析，不修改

适用于需求不清、跨系统、高风险或根因证据不足，输出根因候选、证据和处理建议。

候选级

生成补丁，人工确认

适用于普通功能缺陷。Agent 生成最小补丁、影响说明和测试补充，由研发人员审查应用。

受控执行级

授权范围内自动执行

适用于低风险、边界清晰、测试充分的问题，自动修改后必须完成回归并接受云端审查。

六条修复护栏

修复的目标是恢复正确业务行为，而不是改变测试来适应错误实现。

最小修改优先局部修复，说明每项变化必要性
范围约束只修改授权文件、模块和分支
断言保护禁止删除测试或降低断言强度
规则保护不得擅自改变权限、状态机和数据口径
轮次上限连续失败、归因漂移或越界立即转人工
双重回归原问题验证＋影响范围回归
原失败用例通过＋关联功能回归通过＋无越权修改＋剩余风险已记录＝修复完成

双侧责任边界只服务于闭环控制

云端管理侧不远程做技术实现，本地研发侧也不能自行改变任务目标和风险边界。

本地 Agent ＋ 研发人员

负责具体测试、技术归因、代码修复和本地验证。

  • 决定如何测试、如何定位、如何修改。
  • 确认 Agent 生成的用例、归因和补丁。
  • 超出目标、标准、授权或风险边界时升级。

云端 Agent ＋ 管理人员

云端 Agent 只辅助，管理人员负责目标、标准、边界、风险和放行。

  • 确认验收标准和必测要求。
  • 处理范围调整、豁免和剩余风险。
  • 依据证据决定放行、退回或终止。
06

Functions

核心功能：围绕测试准确性、执行方式和修复闭环组织能力

功能不按测试管理平台菜单堆叠，而是直接支撑“正确性依据—测试设计—多方式执行—失败归因—受控修复—影响回归—审查沉淀”。

测试设计与准确性

01

功能正确性依据管理

统一管理需求、验收标准、业务规则、契约、页面行为和历史缺陷。

›

职责：形成测试设计和通过判定的正式事实源，识别依据缺失、版本不一致和规则冲突。

  • 需求与验收项结构化。
  • 权限、状态、计算和校验规则关联。
  • 接口契约、页面行为和历史缺陷关联。
  • Agent 推断与正式事实分离。
  • 可测试性和依据冲突检查。

验收重点

  • 关键测试断言可追溯到明确依据。
  • 冲突未解决不得形成正式通过结论。
  • 依据版本与任务、代码版本绑定。
02

智能测试策略与模式选择

根据任务类型、风险、代码变更和资产成熟度选择测试方式和控制模式。

›

职责：区分新功能、增量变更、缺陷修复和版本验收，推荐人工辅助、受控自动或严格审查模式。

  • 任务触发模式识别。
  • 需求、变更和历史三类驱动融合。
  • 接口、UI、端到端、权限、状态等方式组合。
  • 测试优先级和执行深度建议。
  • 关键必测项和人工确认点生成。

验收重点

  • 策略能够解释“为什么测这些”。
  • 高风险功能不能降级为无监督自动模式。
  • 研发人员可调整技术方案，管理人员确认目标和边界。
03

测试场景、用例、数据与断言生成

把测试策略转化为可执行且可追溯的测试资产。

›

职责：生成正常、异常、权限、状态、边界、历史缺陷和变更影响场景，并补全步骤、数据和预期结果。

  • 场景与验收项覆盖关系。
  • 前置条件和测试数据约束。
  • 断言来源与置信信息。
  • 自动化可行性判断。
  • 研发人员评审和版本管理。

验收重点

  • 关键验收项不存在无用例覆盖。
  • 不确定断言必须显式标注。
  • 低价值重复用例可识别和清理。
04

环境、数据与多方式测试执行

建立可信执行基线并调用现有测试工具完成真实验证。

›

职责：检查代码、配置、依赖和数据状态，根据测试策略调度接口、UI、端到端、状态和人工辅助测试。

  • 代码、环境和依赖版本绑定。
  • 环境健康和数据前置检查。
  • 现有测试框架与工具适配。
  • 超时、重试、并行和阻塞控制。
  • 日志、截图、响应、状态和耗时采集。

验收重点

  • 测试结论来源于真实工具执行。
  • 环境问题能够与代码缺陷区分。
  • 失败能够复现并保留完整上下文。
05

覆盖分析与多证据测试判定

综合测试结果、业务覆盖和多源证据形成可信测试结论。

›

职责：汇总需求覆盖、场景执行、断言、日志、请求响应、页面证据和状态变化，识别遗漏和冲突。

  • 需求与验收项覆盖矩阵。
  • 通过、失败、阻塞和未执行分类。
  • 证据一致性与缺失检查。
  • 关键路径和未覆盖风险提示。
  • 测试结论及其可信依据生成。

验收重点

  • 不能仅以脚本成功率代替业务正确性。
  • 阻塞和未执行项不得被统计为通过。
  • 管理审查可反查测试依据和原始证据。
06

失败归因与缺陷证据化

区分需求、用例、数据、环境、契约和代码问题，决定正确处理对象。

›

职责：综合多源证据形成候选根因、可信度、影响范围和推荐处理路径。

  • 断言差异、日志和错误堆栈分析。
  • 环境、数据和依赖状态检查。
  • 接口契约和代码 diff 对比。
  • 历史缺陷相似性匹配。
  • 低可信归因转人工确认。

验收重点

  • 失败不默认归为代码缺陷。
  • 归因包含证据和不确定信息。
  • 需求与业务规则问题准确升级。
07

受控智能修复

在研发人员监督和授权范围内生成修复方案、最小补丁和测试补充。

›

职责：根据归因结果选择建议级、候选级或受控执行级修复，控制修改范围、轮次和终止条件。

  • 根因解释和方案比较。
  • 最小补丁和修改说明。
  • 测试补充与影响分析。
  • 删除测试、降低断言和规则绕过检测。
  • 超范围、归因漂移和连续失败自动停止。

验收重点

  • 代码修改由研发人员承担工程责任。
  • 高风险和越界修改必须升级。
  • 修复不允许改变已确认正确性标准。
08

影响范围分析与双重回归

证明原问题解决，并确认相关业务行为未被破坏。

›

职责：根据修改 diff、接口依赖、数据模型、状态机、页面路由和历史缺陷选择回归范围。

  • 原失败用例重跑。
  • 相关接口、页面、权限和状态回归。
  • 历史缺陷和关键冒烟回归。
  • 新增失败识别并重新归因。
  • 回归选择理由和未覆盖风险输出。

验收重点

  • 不能只重跑原失败用例。
  • 已识别影响项必须完成回归或正式豁免。
  • 新增失败自动阻止修复完成判定。
09

云端审查辅助与责任边界控制

云端 Agent 汇总复杂工程事实，辅助管理人员决定目标、边界、风险和放行。

›

职责：管理任务目标、验收标准、必测要求、升级事项和阶段结论，但不替代人员作出正式决定。

  • 测试修复任务包下发。
  • 范围、标准和授权边界管理。
  • 本地升级事项和风险摘要。
  • 放行、退回、豁免和终止记录。
  • 管理意见转化为本地可执行要求。

验收重点

  • 云端 Agent 独立决策数量为零。
  • 正式决定均记录责任人和版本。
  • 本地工程细节原则上由研发人员决定。
10

Trace、证据与知识沉淀

记录全过程并将经过验证的经验转化为可复用项目资产。

›

职责：关联任务、需求、测试、工具、代码修改、回归和人工决定，生成证据包和知识候选。

  • Agent 会话、工具调用和文件变更 Trace。
  • 任务、需求、commit、测试和补丁关联。
  • 本地缓存、断点续传、去重和脱敏。
  • 测试修复证据包和覆盖矩阵。
  • 知识候选审查、版本、发布和失效管理。

验收重点

  • 测试与修复结论可反查完整证据。
  • Trace 不直接等同于正式知识。
  • 知识具有来源、适用范围、版本和责任人。

MVP & Acceptance

第一阶段建设重点：先证明“测试可信＋修复闭环”

第一阶段不自研完整测试引擎，而是接入现有工具，重点证明 Agent 能否基于正确依据设计测试、准确区分失败类型、受控完成修复并形成可复核证据。

核心验证假设

针对一个既有 Web 应用中的明确功能任务，系统能否从需求和代码变更形成高价值测试集，通过真实工具执行识别功能问题，正确区分环境与代码缺陷，在研发人员监督下完成修复和影响回归，并由云端形成可审查证据。
单一 Web 项目接口＋UI测试本地 Agent 工作流受控补丁影响回归Trace 证据

第一阶段纳入

  • 需求、验收项和业务规则关联。
  • 新功能、变更和缺陷三类测试模式。
  • 接口、UI和历史缺陷回归。
  • 测试场景、数据和断言生成。
  • 环境检查、多证据执行和失败归因。
  • 候选补丁、双重回归和云端审查。

第一阶段暂不重点建设

  • 自研完整测试执行引擎。
  • 性能、安全和兼容性测试全覆盖。
  • 复杂跨系统自动修复。
  • 无研发人员监督的高风险代码修改。
  • 无管理人员确认的风险接受与放行。
  • 大规模跨项目知识自动发布。
